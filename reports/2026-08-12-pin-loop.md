# 2026-08-12 — The pin loop through the app

The onboarding build line's first item (approved 2026-08-12): the
human's answer to a definitional question lands in the HUMAN slot by
one gesture, through the app — closing F3 of the glos evaluation,
where the actor model's centerpiece was unreachable from the flows
that need it and a relayed answer landed as an agent gloss at 0.85.

## What landed

**The pin door** (`crates/apps/src/pin.rs`, `POST /app/<name>/pin`).
The app door's first and only write: a form carrying (subject,
aspect, body, pinned_by) becomes one `GLOSS` statement executed on a
Human channel whose actor id is the pinner's name (unauthenticated by
design — the name is provenance, not permission; unsigned pins fall
back to `app:<name>`). Everything about the write is the ordinary
gloss path — aspect schema validation, grain gating, the witness
speaker gate, ACCEPTS invalidation — the door composes and decides
nothing. Guards, in the review's spirit: path-subject and aspect
names are strict identifier segments; the body must parse as JSON and
its serialization must not carry `$$` (after the dollar-quote
terminator, further text would parse as further statements — the
smuggle is refused, with a test aiming a `DELETE FROM glossary` at
it). htmx callers get `HX-Refresh`; plain forms get a local-only
redirect.

**The `pin_questions` convention** (taught in glossql-metrics §9).
The pinning agenda, which already ends every metrics flow, now also
lands as a FACT gloss on the dataset — flat, one entry per option,
each carrying the full body its approval would write. Definitional
pins ride the `definitions` gloss ruled the same day, so a pin is the
definition of record changing hands, not a side-channel note.

**The queue in the model app** (`frames/pins.sql`, a tile on the
standing view). One row per open option, the house unnest pattern
(`generate_series` + `json_get`), a pin form per row with a shared
"sign it" name field (`hx-include`). Answered questions leave by
derivation — the frame anti-joins the `glossary` relation for a human
slot on the question's (subject, aspect) — never by mutating the
agenda. `gl-rows` now hands inserted rows to htmx (`htmx.process`),
which any future interactive row template inherits.

**The loop, tested end to end**
(`crates/apps/tests/door.rs::the_pins_frame_serves_the_agenda_and_empties_on_answer`):
agent glosses a two-option agenda → the built-in model app serves two
rows → a signed pin writes the HUMAN slot (verified under the
pinner's name, outranking the agent slot in the collapsed read) →
the queue serves zero rows. Plus refusal tests for the smuggle
shapes and a direct HUMAN-slot write test.

## Found on the way

The builtin registry (`crates/apps/src/builtin.rs`) had drifted from
the model app's directory: `frames/bands.sql`, `frames/scenarios.sql`
and `specs/bands.vl.json` existed on disk and were referenced by the
index page but were never embedded — served 404 from the binary, and
excluded from the frame-parse suite. Added; the registry now matches
the directory.

## Left open, named

- The assumptions tile still teaches the relay ("rule it in your own
  session") — an assumptions pin needs the full metric gloss
  recomposed, which only the agent holds; the queue's `pin_questions`
  entries are where the agent pre-composes bodies for approval. If
  assumption pins want the one-gesture path, the agenda is the way:
  gloss them as questions.
- Pair-path subjects don't pin (path subjects only, v1) — until a
  surface needs them.
- One Human channel per distinct pinner name — the known
  session-per-actor growth, bounded at PoC scale.
- Recipe-borne corrections (F6) were approved to ride this surface;
  the approval body for a recipe change is not yet designed — it
  follows when the correction flow produces proposals as data the
  way the agenda does.
